# InterviewPrep — Feature 1

This document describes Feature 1: custom email/password signup, login, logout,
and the protected welcome page. Feature 2 subsequently added the question-type
reference list and practice-session schema; see `schema.md` for the current
database and startup-seeding behavior. The original `README.md` and `PLAN.md`
are preserved.

## Run and architecture

Use the managed `artifacts/interviewprep: web` workflow in Replit Preview. One Express process serves React and all `/api` routes. During development, Vite is mounted inside Express. In production, Express serves the built React files. The exported app in `artifacts/interviewprep/server/app.mjs` can be imported without starting a listener. `server/index.mjs` starts the listener.

Setup's shared libraries, API scaffold and design sandbox are retained. The unused API scaffold has no public routing paths, so it cannot intercept authentication or expose a public `/api/healthz` endpoint. It is not needed to run the product. Future product API routers belong below the auth boundary in `artifacts/interviewprep/server/app.mjs`, not in the unused scaffold.

Dependencies: Node.js 24, pnpm, Replit PostgreSQL and `SESSION_SECRET`. Run `pnpm install --frozen-lockfile` after checkout. `scripts/post-merge.sh` applies the development-only SQL schema, now including the two Feature 2 tables described in `schema.md`. Schema changes never run during app startup or a production build.

## Production schema provisioning — required before serving traffic

Replit's **Publish flow**, not the app or the development post-merge hook, owns production database provisioning. For the first publish it creates the managed production database; on publish it compares the development and production schemas and applies the required changes. Startup-time SQL or a custom production migration hook would conflict with this supported process.

When you choose to publish later:

1. Complete development setup and verify the development database contains the approved `users` and `login_sessions` tables.
2. In Publishing, select the Replit-managed production database for this app, with `DATABASE_URL` configured by Replit. Make `SESSION_SECRET` available securely to the production environment.
3. Review the schema comparison and apply the approved tables before the release serves requests, including Feature 2 tables when publishing that version. Review proposed schema changes rather than copying development account data.
4. Confirm the production schema has both tables before testing `/api/auth/status`, signup, refresh and logout. Do not test or serve against a blank, unprovisioned database.

No publishing or writes to a production database were performed for this task. The repeatable production-settings test uses a **fresh isolated schema in the development database**, installs the approved schema before traffic, then runs the app with `NODE_ENV=production` and checks signup, secure cookies, refresh, logout invalidation and login. It removes the temporary schema afterward. This tests application behavior, not Replit's actual Publish flow.

Official platform reference: https://docs.replit.com/features/data-and-storage/development-and-production

## SESSION_SECRET in Replit

This workspace already lists the secret; do not replace it unnecessarily.

1. Open **Tools → Secrets** under **Setup** in the Project Editor.
2. Choose **New Secret** and use the key `SESSION_SECRET`.
3. In the secure value field, enter a cryptographically random value of at least 32 bytes, generated by a trusted password manager. Never paste it in chat or commit it.
4. Click **Add Secret**, then restart the managed product workflow.

The server reads this environment variable and refuses to start without it. Replacing it invalidates old login cookies. Official instructions: https://docs.replit.com/core-concepts/project-editor/app-setup/secrets

## From clicking to the database

**Initial page check:** React asks `/api/auth/status` whether the browser has a valid session. Express verifies the signed httpOnly cookie and reads its session from PostgreSQL. The response contains only user id/email (or no user) and a session-bound security token. Private content stays hidden until the check finishes.

**Sign up:** The form checks email, password and confirmation, then sends them over the same origin with that security token. The server validates again, trims/lowercases the email and hashes the password with bcrypt cost 12. A parameterized INSERT saves only email and the hash in `users`. PostgreSQL's unique constraint safely rejects duplicates even when requests arrive simultaneously. Express replaces the session id, saves the user id in `login_sessions`, and sends a signed cookie. React opens the welcome page with your normalized email.

**Log in:** The server normalizes the email, retrieves the account and uses bcrypt to compare the submitted password with the stored hash. Wrong email and wrong password return the same credentials error. Success replaces and saves the session before returning only id/email. Refreshing restores authentication through the cookie and PostgreSQL session.

**Log out:** React sends a security-token-protected POST. The server deletes the session from PostgreSQL and clears the browser cookie. React clears the signed-in state and returns to login. The old cookie can no longer access protected APIs.

Passwords and hashes are never returned in API responses or logged. No plain-text password is stored. Cookies last up to seven days, are httpOnly and SameSite=Lax, and require HTTPS in production. Preview and production trust one proxy hop. Signup/login are limited to 40 attempts per IP per 15 minutes per process; this counter resets on restart and is not shared across multiple instances.

Only `/api/auth/status`, `/api/auth/signup` and `/api/auth/login` are public. All future APIs must be registered below `app.use('/api', requireAuth)`. Unknown API routes are protected too. Mutations require a session-bound CSRF token.

## Manual testing

1. Open Preview at `/` in a fresh private window. Expect `/login` without a flash of the welcome page.
2. Click **Create an account** and submit empty fields. Expect **Please fill in all fields.**
3. Submit a malformed email with a password and confirmation. Expect a clear inline email-format error.
4. Use a valid email with matching passwords shorter than eight characters. Expect **Password must be at least 8 characters.**
5. Use a valid-length password and different confirmation. Expect **Passwords don't match.**
6. Use a new mixed-case email and matching valid passwords. Submit. Expect **Welcome to InterviewPrep** and the email in lowercase.
7. Refresh. The welcome page and email should remain. Visit `/login` while signed in; you should return to `/`.
8. Click **Log out**. On a phone, open the header menu first. Expect `/login`. Visiting `/` again must redirect to login.
9. Try signup with the same email using different capitalization. Expect **An account with this email already exists. Try logging in.**
10. Try login with a wrong password, then an unregistered email and a valid-length password. Both must show **Email or password is incorrect.**
11. Log in with the correct credentials. Expect the welcome page. Log out again.
12. While logged out, open `/api/me` and `/api/a-future-route`. Both must return HTTP 401 without user data.
13. Repeat at approximately 375px and laptop width. Check no horizontal scrolling, 44px minimum inputs/buttons, keyboard focus and mobile logout access.
14. In Replit's development Database pane, verify the four approved tables described in `schema.md`. Verify lowercase emails and bcrypt hashes, not submitted passwords. Do not copy passwords or hashes into chat.

New accounts require at least eight characters and at least one special character
(punctuation or a symbol, such as `!`, `@`, `#`, or `-`). Spaces alone do not
satisfy the special-character rule. The signup form and server both enforce it
and show “Password must include at least one special character (for example, !, @, or #).”
Existing accounts without special characters can still log in with their current
passwords. To test the new rule, try signing up with a letters-and-digits-only
password, then add a special character and submit again.

Bcrypt ignores bytes after 72; the app rejects passwords over 72 UTF-8 bytes instead of silently treating different passwords as equivalent.

## Automated checks

- `pnpm test`: PostgreSQL integration tests for validation, hashing, safe response fields, CSRF, cookies, session rotation/persistence, logout invalidation, login, concurrent duplicates and approved tables.
- The same command also runs `server/production.test.mjs`, verifying production settings against a newly provisioned, isolated development schema.
- `pnpm typecheck`: full workspace TypeScript checks.
- `pnpm build`: full workspace production build.
- `pnpm --filter @workspace/interviewprep test:browser`: real browser flows at 375px and 1366px, including inline errors, signup, refresh, redirects, logout, duplicate emails, login, touch sizes and no overflow. Requires a running product workflow and system Chromium; use `CHROMIUM_PATH` to override the executable. Uses `REPLIT_DEV_DOMAIN` or an explicit `TEST_BASE_URL`.

Tests create uniquely named accounts and remove only those test accounts and associated authenticated sessions. The app has not been published.
